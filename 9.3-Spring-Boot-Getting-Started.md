## Spring Boot folder structure

When you create a standard Spring Boot project (typically via Spring Initializr), it follows a **Maven** or **Gradle** standard directory layout. This structure is designed to separate your source code, configuration, and testing logic cleanly.

### Standard Maven Project Structure

Below is the conventional layout you will see in a production-grade Spring Boot application:

```text
my-spring-app/
├── src/
│   ├── main/
│   │   ├── java/
│   │   │   └── com/example/demo/
│   │   │       ├── DemoApplication.java      <-- Entry point (@SpringBootApplication)
│   │   │       ├── controller/               <-- API Endpoints
│   │   │       ├── service/                  <-- Business Logic
│   │   │       ├── repository/               <-- Data Access (JPA/Mongo)
│   │   │       ├── model/                    <-- Entities/POJOs
│   │   │       ├── dto/                      <-- Data Transfer Objects
│   │   │       ├── config/                   <-- Bean Configurations
│   │   │       └── exception/                <-- Custom Exception Handling
│   │   ├── resources/
│   │   │   ├── static/                       <-- CSS, JS, Images (for UI)
│   │   │   ├── templates/                    <-- HTML Templates (Thymeleaf)
│   │   │   └── application.properties        <-- App Config (or application.yml)
│   └── test/
│       └── java/
│           └── com/example/demo/             <-- Unit and Integration Tests
├── target/                                   <-- Compiled bytecode (generated)
├── pom.xml                                   <-- Maven Dependencies
└── mvnw                                      <-- Maven Wrapper script
```

---

### Key Directories Explained

#### 1. src/main/java
This is where your actual logic lives. For a Senior/Staff level approach, it is highly recommended to follow **Layered Architecture**:
* **Controller Layer:** Handles HTTP requests and mapping.
* **Service Layer:** The "brain" of your app. Transaction management (`@Transactional`) happens here.
* **Repository Layer:** Interface with the database.
* **Application Class:** Usually sits in the root package (e.g., `com.example.demo`) so that `@ComponentScan` can find all your beans automatically.

#### 2. src/main/resources
* **application.properties / .yml:** This is where you define your database URL, server port, and custom properties.
* **static vs templates:** Use `static` for files that don't change (plain HTML/JS). Use `templates` if you are using a server-side engine like Thymeleaf.

#### 3. src/test
Spring Boot treats testing as a first-class citizen. You will typically find `DemoApplicationTests.java` here, which uses `@SpringBootTest` to verify that the application context loads correctly.

### Multi-Module Structure (Advanced)
In larger enterprise environments (like the ones you've worked in at PayPal or Disney+), you might see a **Multi-Module** setup to enforce strict boundaries between components.

```text
root-project/
├── api-gateway/          <-- WebFlux/Gateway logic
├── core-service/         <-- Shared business logic/models
├── data-access-lib/      <-- Common DB configs
├── pom.xml               <-- Parent POM managing versions
└── build.sh
```

### Pro-Tip
Ensure your package naming follows a domain-driven or feature-driven approach if the project is large. Instead of putting everything in one giant `service` folder, you might group by feature:
* `com.example.demo.payment`
* `com.example.demo.user`
* `com.example.demo.order`

This makes the code much easier to navigate and eventually split into microservices if needed. 

## What is pom.xml?

In a Spring Boot application, the **pom.xml** (Project Object Model) is essentially the **"Recipe and Instruction Manual"** for your project. It is used by **Maven**, a tool that automates the building, testing, and packaging of your Java code.

If you think of your application as a Lego set, the `pom.xml` is the list of all the bricks you need and the instructions on how to snap them together.

### The Anatomy of a pom.xml

Here is a simplified look at the main sections:

```text
<project>
  │
  ├── Parent (The "Base Recipe")
  │   └── spring-boot-starter-parent
  │
  ├── Project Identity (The "DNA")
  │   ├── GroupId: com.paypal
  │   ├── ArtifactId: cms-service
  │   └── Version: 1.0.0
  │
  ├── Dependencies (The "Ingredients")
  │   ├── spring-boot-starter-web
  │   ├── spring-boot-starter-data-jpa
  │   └── spring-boot-starter-test
  │
  └── Build (The "Kitchen Tools")
      └── spring-boot-maven-plugin
</project>
```

### Key Sections Explained

#### 1. The Parent (The Foundation)
Most Spring Boot `pom.xml` files start with a `<parent>` tag.
* **Why it exists:** It provides default configurations (like Java version and encoding) so you don't have to write them yourself. It also manages versions for hundreds of libraries, ensuring they all play nicely together without "dependency hell."

#### 2. Dependencies (External Libraries)
This is the most visited part of the file. Instead of downloading `.jar` files manually, you list them here.
* **Starters:** Spring Boot uses "Starters" (e.g., `spring-boot-starter-web`). These are like "Combo Meals"—one dependency that automatically pulls in everything needed to build a web app (like Tomcat, Jackson for JSON, and Spring MVC).

#### 3. Properties (Global Variables)
This section acts as a "Settings" panel. You can define a Java version here once:
```xml
<properties>
    <java.version>17</java.version>
</properties>
```
All other parts of the project will now know to use Java 17.

#### 4. The Spring Boot Maven Plugin
Located in the `<build>` section, this is the "Magic Wand." 
* It allows you to run your app with a simple command like `mvn spring-boot:run`.
* It packages your entire application (including the server) into a single, executable **FAT JAR** that you can deploy anywhere.

### Why is it useful?
In high-scale environments, the `pom.xml` is where you would:
* Exclude conflicting libraries.
* Manage versions for internal shared libraries.
* Configure plugins for code coverage (Jacoco) or static analysis (SonarQube).

## Creating a simple REST endpoint

1. Add an annotation `@RestController` to your Spring Boot Application class
2. Create a method that returns a response
3. Add an annotation `@GetMapping` to this method
4. Run the application and open `localhost:8080` (the default port)

```java
// DemoApplication.java

// ... imports

@SpringBootApplication
@RestController
public class DemoApplication {

	public static void main(String[] args) {
		SpringApplication.run(DemoApplication.class, args);
	}

	@GetMapping
	public String helloWorld() {
		return "Hello World!";
	}
}
```

## Creating a Controller

In order to handle specific API endpoints, we create "controllers" in Java
1. Create a new class, by convention suffix the name with `Controller` (Ex: `TodoController`), add this annotation for it: `@RestController`
2. Add another annotation: `@RequestMapping`
3. Provide a path argument to this annotation: Ex: `@RequestMapping("api/v1/software-engineers")`

```java
// Spring Boot Starter class
@SpringBootApplication
@RestController
public class DemoApplication {

	public static void main(String[] args) {
		SpringApplication.run(DemoApplication.class, args);
	}

	@GetMapping
	public String helloWorld() {
		return "Hello World!";
	}
}
```

```java
// New controller class
@RestController
@RequestMapping("api/v1/software-engineers")
public class SoftwareEngineerController {

    @GetMapping
    public List<SoftwareEngineer> getEngineers() {
        return List.of(
                new SoftwareEngineer(1, "James", "Java"),
                new SoftwareEngineer(2, "Pushkar", "JavaScript")
        );
    }
}
```

```java
// New class for handling data (sample): This would ideally be a DTO
// Add the private fields and right click, use generators to generate 
// the constructor, getters and setters, equals and hashcode
package com.example.demo;

import java.util.Objects;

public class SoftwareEngineer {
    private Integer id;
    private String name;
    private String techStack;

    public SoftwareEngineer() {}

    public SoftwareEngineer(Integer id, String name, String techStack) {
        this.id = id;
        this.name = name;
        this.techStack = techStack;
    }

    public Integer getId() {
        return id;
    }

    public void setId(Integer id) {
        this.id = id;
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }

    public String getTechStack() {
        return techStack;
    }

    public void setTechStack(String techStack) {
        this.techStack = techStack;
    }

    @Override
    public boolean equals(Object o) {
        if (o == null || getClass() != o.getClass()) return false;
        SoftwareEngineer that = (SoftwareEngineer) o;
        return Objects.equals(id, that.id) && Objects.equals(name, that.name) && Objects.equals(techStack, that.techStack);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, name, techStack);
    }
}
```

## Equals and hashcode generation

In Java, `equals()` and `hashCode()` are the foundation of object comparison and data storage in collections like `HashMap` and `HashSet`. Since you've provided a `SoftwareEngineer` class with these methods overridden, let's break down how they work and what the generated values actually represent.

### The `equals` Method (Equality by Value)
By default, the `Object` class uses `==` comparison, which checks if two references point to the same memory address. By overriding it as you have, you’ve implemented **Value Equality**.

* **Logic:** Two `SoftwareEngineer` objects are considered "the same" if their `id`, `name`, and `techStack` are identical.
* **The Check:** You used `Objects.equals(a, b)`, which is the "senior" way to do it—it handles `null` checks internally to prevent `NullPointerException`.

### The `hashCode` Method (The Fingerprint)

The `hashCode()` method returns an integer representation of the object. Think of it as a "digital fingerprint" used primarily by hash-based collections to find where to store your object.

* **How it's generated:** `Objects.hash(id, name, techStack)` takes the values of those three fields and runs them through a mathematical formula (usually involving prime numbers like 31).
* **The Result:** If two objects are equal according to `equals()`, they **must** return the same `hashCode`.

### How they work together (The HashMap Contract)

When you put a `SoftwareEngineer` into a `HashMap`, Java doesn't loop through every entry to see if it exists. Instead, it follows this workflow:

1. **Step 1:** It calls `hashCode()` on your object to determine which "bucket" it belongs in.
2. **Step 2:** If there are multiple objects in that bucket (a **collision**), it then calls `equals()` to find the exact match.

### Summary Table: Why both?

| Scenario | Result of `equals()` | Result of `hashCode()` | Behavior |
| :--- | :--- | :--- | :--- |
| **Identical Objects** | `true` | Must be identical | Correctly identified as a duplicate in a `Set`. |
| **Hash Collision** | `false` | Can be identical | Two different engineers end up in the same bucket; Java uses `equals` to tell them apart. |
| **Inconsistent Overriding** | `true` | Different | **Bug!** You could add the "same" engineer to a `HashSet` twice because they'd land in different buckets. |

### Pro-Tip

In modern Java (14+), if this class is strictly for carrying data, you can replace the entire 40+ lines of code with a **Record**:

`public record SoftwareEngineer(Integer id, String name, String techStack) {}`

This automatically generates the constructor, getters, `equals`, `hashCode`, and `toString` for you using the same logic you've written manually. 

## Starting a Database server using Docker

Prerequisite: Learn the basics of docker compose 
1. Create a `docker-compose.yml` (Create it in the project root)
2. Use an existing image (such as of Postgres from docker hub)
3. Create a volume on the host machine to persist the DB data (map it)
4. (Optional) Create a virtual network using the "bridge" mechanism for an isolated network
5. Run this DB container in the background (`docker compose up -d` where `-d` is detached mode)

```
services:
  db:
    container_name: postgres-spring-boot
    image: postgres:latest
    environment:
      POSTGRES_USER: pushkar
      POSTGRES_PASSWORD: 123456
      PGDATA: /data/postgres
    volumes:
      - db:/data/postgres
    ports:
      - 5332:5432
    networks:
      - db
    restart: unless-stopped

networks:
  db:
    driver: bridge

volumes:
  db:
```

### Understanding "networks"

This snippet defines a **custom virtual network** within your Docker environment. In simple terms, it creates a private "chat room" or "switch" specifically for your database and any other services you connect to it.

#### Breakdown of the Code

* **`networks:`**: This is the top-level key where you define all the communication channels for your stack.
* **`db:`**: This is the **User-Defined Name** for your network. You could name it `backend-net` or `data-layer`, but `db` is a common convention for clarity.
* **`driver: bridge`**: This specifies the network type. The `bridge` driver is the most common. It creates an internal network on your host machine so that containers on this network can talk to each other while remaining isolated from other containers not on this network.

#### How it looks in a full file
Defining a network isn't enough; you have to **attach** your services to it. Here is how you would use it to connect a Spring Boot app to a PostgreSQL database:

```yaml
services:
  database:
    image: postgres:15
    networks:
      - db  # Joining the private room

  app-service:
    image: my-spring-app:latest
    networks:
      - db  # Joining the same room to talk to the DB
    depends_on:
      - database

networks:
  db:
    driver: bridge
```

#### Why use a custom network instead of the default?

| Feature | Default Docker Network | Custom Bridge Network (Your Code) |
| :--- | :--- | :--- |
| **Service Discovery** | No. You must use IP addresses. | **Yes.** You can use the service name (e.g., `jdbc:postgresql://database:5432/`). |
| **Isolation** | All containers on the host can potentially talk. | Only containers explicitly listed under `networks` can talk. |
| **Security** | Lower. | Higher. You keep your DB off the default public bridge. |

#### Pro-Tip
In a production-grade setup, you would typically define two networks:
1.  **Frontend/Public Network:** For your Web/API layer to talk to the internet.
2.  **Backend/Private Network (your `db` network):** For your API to talk to the Database. 

This ensures your database is "air-gapped" from the public web, as it doesn't even need to be on the network that receives external traffic.

## Performing CRUD operations on DB using Spring JPA

Spring Data JPA is a framework that simplifies database interactions in Spring applications.
- It provides a high-level abstraction
- Reduces boilerplate code 
- Enables easy implementation of CRUD operations

Technically, **Spring Data JPA is not an ORM itself**; rather, it is a high-level **abstraction layer** that makes it significantly easier to use an ORM.

### JPA (The Specification)
**Java Persistence API (JPA)** is just a set of rules and interfaces (a specification). It defines *how* an object should be mapped to a database table using annotations like `@Entity`, but it contains no actual code to perform the database operations.

### Hibernate (The ORM)
**Hibernate** is the actual **ORM (Object-Relational Mapper)**. It is the engine that implements the JPA specification. It contains the logic to generate SQL, manage transactions, and map Java objects to table rows.

### Spring Data JPA (The Abstraction)
**Spring Data JPA** sits on top of Hibernate. Its primary job is to remove the "boilerplate" code. Instead of writing complex DAO (Data Access Object) implementations with an `EntityManager`, you simply create an interface that extends `JpaRepository`.

### Key Differences at a Glance

| Feature | JPA | Hibernate | Spring Data JPA |
| :--- | :--- | :--- | :--- |
| **Type** | Specification | ORM Framework | Abstraction Library |
| **Role** | Defines the "What" | Implements the "How" | Simplifies the "Usage" |
| **Code** | Interface only | Heavy lifting (SQL generation) | Repository interfaces and Query Methods |

### How they work together in your project
In a standard Spring Boot application, the relationship looks like this:

1.  **You** define an `@Entity` (JPA)
2.  **You** create a `UserRepository` interface (Spring Data JPA)
3.  **Spring Data JPA** generates the implementation at runtime
4.  **Hibernate** (***the default ORM***) takes those instructions and talks to your PostgreSQL or MySQL database

### Why use Spring Data JPA if Hibernate does the work?

Spring Data JPA allows for **Query Methods**. Instead of writing SQL or HQL, you can simply name a method `findByEmailAddressAndLastname(String email, String lastname)`, and Spring will automatically derive the query for you.

```
+-------------------------------------------------------+
|                 YOUR APPLICATION CODE                 |
|      (Uses: @Repository, JpaRepository interface)      |
+--------------------------|----------------------------+
                           v
+-------------------------------------------------------+
|                 SPRING DATA JPA (Layer)               |
|    - High-level abstraction                           |
|    - Generates boilerplate DAO implementation         |
|    - Translates method names (findByID) into queries  |
+--------------------------|----------------------------+
                           v
+-------------------------------------------------------+
|                 JPA SPECIFICATION (API)               |
|    - The standard "Rules" (javax.persistence.*)       |
|    - Defines annotations: @Entity, @Table, @Id        |
+--------------------------|----------------------------+
                           v
+-------------------------------------------------------+
|                 HIBERNATE (The ORM)                   |
|    - The "Engine" that implements JPA                 |
|    - Generates actual SQL (SELECT, INSERT, etc.)      |
|    - Manages the Persistence Context / Cache          |
+--------------------------|----------------------------+
                           v
+-------------------------------------------------------+
|                   JDBC / DB DRIVER                    |
|    - Low-level connection to the physical Database     |
+-------------------------------------------------------+
```

Example "Save" operation: When you call repository.save(user), here is the path that request takes:
```
[ Java Object ]      [ Spring Data JPA ]      [ Hibernate / ORM ]      [ Database ]
       |                       |                        |                     |
       |--- .save(user) ------>|                        |                     |
       |                       |--- Magic happens: ---->|                     |
       |                       |    Determines if new   |                     |
       |                       |    or update.          |                     |
       |                       |                        |-- Generate SQL ---->|
       |                       |                        |   INSERT INTO...    |
       |                       |                        |                     |
       |                       |<--- SQL Success -------|                     |
       |<--- Returned Object --|                        |                     |
```

### Performing CRUD on DB tables

1. Create a new **Interface** (New class > Type "Interface")
    - This is going to be a "Repository", ***extending*** a `JpaRespository` class
    - It is the ***layer that abstracts away talking to the DB***
    - It needs two arguments while extending:
        1. The "entity" to map to, and the 
        2. Data type of the primary key of the entity
    - It provides methods to interact with the DB by default such as a `.findAll`, `.findBy`, etc
2. Create a new **Service** (Regular class)
    - It is the layer that ***deals with the business logic***
    - Add the **`@Service`** annotation to this class
        - Spring boot creates a bean for it and lets other classes use it
    - Instantiate the repository created for the entity in step 1
        - Do it using the constructor!
    - Write all your business logic within methods here using the in-built functions of the repository!
3. Back in the **controller** (`@RestController`), interact with the ***service*** from one of the request handler methods

```java
// SoftwareEngineerRepository

package com.example.demo;

import org.springframework.data.jpa.repository.JpaRepository;

public interface SoftwareEngineerRepository extends JpaRepository<SoftwareEngineer, Integer> {
}

```

```java
// SoftwareEngineerService

package com.example.demo;

import org.springframework.stereotype.Service;

import java.util.List;

@Service
public class SoftwareEngineerService {

    private SoftwareEngineerRepository softwareEngineerRepository;

    public SoftwareEngineerService(SoftwareEngineerRepository softwareEngineerRepository) {
        this.softwareEngineerRepository = softwareEngineerRepository;
    }

    public List<SoftwareEngineer> getSoftwareEngineers() {
        // Note: Usually you do not want to do this i.e return the DB object as is to the client
        // You would massage and re-format the object and only send what is required back to the client,
        // hiding the sensitive data.
        return softwareEngineerRepository.findAll();
    }
}
```

```java
// SoftwareEngineerController
package com.example.demo;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

import java.util.List;

@RestController
@RequestMapping("api/v1/software-engineers")
public class SoftwareEngineerController {

    private final SoftwareEngineerService softwareEngineerService;

    public SoftwareEngineerController(SoftwareEngineerService softwareEngineerService) {
        this.softwareEngineerService = softwareEngineerService;
    }

    @GetMapping
    public List<SoftwareEngineer> getEngineers() {
        return softwareEngineerService.getAllSoftwareEngineers();
    }
}
```

## Types of JPA repository interfaces

In Spring Data JPA, there is a hierarchy of interfaces. You choose which one to extend based on how much "power" or functionality you need for your database operations.

### The Interface Hierarchy

Think of it as a nesting doll where each level adds more features.

```text
  Repository (The Base)
      |
  CrudRepository (The Basic Actions)
      |
  PagingAndSortingRepository (The Organizer)
      |
  JpaRepository (The Swiss Army Knife)
```

### 1. Repository
**What it is:** The top-level "marker" interface.
**Simple Explanation:** It doesn't actually have any methods. It just tells Spring, "Hey, manage this class as a repository."
**Use Case:** Use this if you want to be extremely strict and only expose specific methods you define yourself.

### 2. CrudRepository
**What it is:** The basic "Create, Read, Update, Delete" interface.
**Simple Explanation:** It provides the standard methods you’d expect for any database.
**Common Methods:** `save()`, `findById()`, `existsById()`, `findAll()`, `deleteById()`.
**ASCII View:**
```text
[ CrudRepository ]
  - save(entity)
  - findById(id)
  - delete(entity)
  - count()
```

### 3. PagingAndSortingRepository
**What it is:** An extension of `CrudRepository` that adds organization.
**Simple Explanation:** It handles large amounts of data. Instead of fetching 1 million rows, it allows you to fetch "Page 1" or "Sort by Name."
**Common Methods:** `findAll(Pageable pageable)`, `findAll(Sort sort)`.
**ASCII View:**
```text
[ PagingAndSortingRepository ]
  - findAll(Sort)
  - findAll(Pageable)  <-- (Limit, Offset, Sort combined)
```

### 4. JpaRepository
**What it is:** The most common and powerful interface.
**Simple Explanation:** It inherits everything above and adds JPA-specific features like flushing the persistence context or deleting records in batches.
**Common Methods:** `flush()`, `saveAndFlush()`, `deleteAllInBatch()`.
**ASCII View:**
```text
[ JpaRepository ]
  - flush()              (Force write to DB)
  - saveAndFlush()       (Save and commit NOW)
  - deleteAllInBatch()   (Efficient mass delete)
```

### Summary: Which one should you use?

| If you want... | Use this Interface |
| :--- | :--- |
| **Complete Control** | `Repository` |
| **Standard CRUD** | `CrudRepository` |
| **Pagination/Sorting only** | `PagingAndSortingRepository` |
| **Full Power (Recommended)** | `JpaRepository` |

**Senior Tip:** Most developers default to `JpaRepository` because it includes everything. However, if you are building a read-only service, extending a custom interface that only exposes `findById` and `findAll` is a cleaner architectural choice to prevent accidental deletes!
